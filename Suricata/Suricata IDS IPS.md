Вводимо в HOME-NET ip нашого діапазону ВМ і основної системи.
- **`/24`** — це діапазон із **254 пристроїв** (від `.1` до `.254`). Перша (`.0`) і остання (`.255`) адреси зарезервовані системою.

- **Дві мережі у списку** — ми наказали Suricata захищати два окремі сегменти вашої мережі (`192.168.0.X` та `192.168.56.X`).

- **Головна мета** — задати змінну **`HOME_NET`** ("свої"). Усе, що входить у цей список, Suricata вважає вашою внутрішньою мережею, а все інше — зовнішнім інтернетом (**`EXTERNAL_NET`**).

Також змінюєм якщо потрібно і при необхідност і додаєм наступні параметри якщо їх немає:

**`interface: enp0s3`**  
Вказує, на якому мережевому інтерфейсі слухати трафік. Робимо це, щоб Suricata знала, звідки саме брати пакети для аналізу.
**`cluster-id: 99`**  
Унікальний ідентифікатор для групування потоків захоплення. Робимо це, щоб при кількох процесах/потоках Suricata на одному інтерфейсі вони коректно ділили між собою трафік, не конфліктуючи.
**`cluster-type: cluster_flow`**  
Визначає спосіб розподілу пакетів між потоками — тут по флоу (сесії/з'єднанню). Робимо це, щоб усі пакети одного з'єднання йшли в один і той самий потік обробки, інакше Suricata не зможе правильно відстежувати стан з'єднання (TCP-сесії, реасемблінг тощо).
**`defrag: yes`**  
Вмикає дефрагментацію IP-пакетів (збирання розбитих на фрагменти пакетів в один цілий). Робимо це, щоб правильно аналізувати трафік, який був фрагментований (інакше сигнатури можуть не спрацювати або спрацювати неправильно на частину пакета).
**`use-mmap: yes`**  
Вмикає використання пам'яті через mmap замість звичайного копіювання пакетів. Робимо це для продуктивності — зменшує навантаження на CPU і прискорює захоплення трафіку на високих швидкостях.
**`tpacket-v3: yes`**  
Вмикає новішу версію протоколу захоплення пакетів у ядрі Linux (TPACKET_V3). Робимо це, щоб отримати кращу продуктивність при захопленні великих обсягів трафіку порівняно зі старішою версією.

# Структура правила (сигнатури) Suricata

Кожне правило Suricata складається з трьох основних частин:

1. **Action (дія)** — визначає, що відбувається при спрацюванні правила
2. **Header (заголовок)** — визначає протокол, IP-адреси, порти і напрямок трафіку
3. **Rule options (опції правила)** — деталізують, за чим саме "полює" правило

---

## Приклад правила

```
alert http $HOME_NET any -> $EXTERNAL_NET any (msg:"HTTP GET Request Containing Rule in URI"; flow:established,to_server; http.method; content:"GET"; http.uri; content:"rule"; fast_pattern; classtype:bad-unknown; sid:123; rev:1;)
```

---

## 1. Action — `alert`

```
alert
```

Каже Suricata, що робити при збігу з правилом. Основні варіанти дій:

|Дія|Що робить|
|---|---|
|`alert`|Записати спрацювання в лог (алерт), трафік не блокується|
|`drop`|Тихо відкинути пакет (тільки в IPS-режимі)|
|`reject`|Відкинути пакет і надіслати відповідь (RST/ICMP unreachable)|
|`pass`|Пропустити трафік без подальшої перевірки іншими правилами|

У нашому прикладі — `alert`, тобто правило тільки фіксує подію, нічого не блокує.

---

## 2. Header — `http $HOME_NET any -> $EXTERNAL_NET any`

Визначає **протокол, адреси, порти і напрямок** трафіку, до якого застосовується правило.

```
http $HOME_NET any -> $EXTERNAL_NET any
```

|Елемент|Значення|Пояснення|
|---|---|---|
|`http`|Протокол|Правило застосовується тільки до HTTP-трафіку (не до будь-якого TCP)|
|`$HOME_NET`|Джерело (IP)|Адреси з внутрішньої мережі (визначені в `vars`)|
|`any`|Джерело (порт)|Будь-який вихідний порт|
|`->`|Напрямок|Односторонній напрямок: від джерела до призначення|
|`$EXTERNAL_NET`|Призначення (IP)|Будь-яка зовнішня адреса (все, що не HOME_NET)|
|`any`|Призначення (порт)|Будь-який порт призначення|

**Простими словами:** правило дивиться на HTTP-трафік, що йде **з внутрішньої мережі назовні** (наприклад, коли клієнт у локальній мережі робить HTTP-запит до зовнішнього сервера).

---

## 3. Rule options — все, що в дужках

```
(msg:"HTTP GET Request Containing Rule in URI"; flow:established,to_server; http.method; content:"GET"; http.uri; content:"rule"; fast_pattern; classtype:bad-unknown; sid:123; rev:1;)
```

|Опція|Значення|Пояснення|
|---|---|---|
|`msg:"..."`|Текст повідомлення|Текст, який з'явиться в алерті — пояснює, що саме виявлено|
|`flow:established,to_server`|Стан з'єднання|Спрацьовує тільки на вже встановлене TCP-з'єднання, і тільки на пакети, що йдуть **до сервера** (не у відповідь)|
|`http.method`|Поле для перевірки|Каже Suricata дивитись саме на HTTP-метод запиту|
|`content:"GET"`|Шуканий вміст|Перевіряє, чи метод запиту дорівнює `GET`|
|`http.uri`|Поле для перевірки|Каже Suricata дивитись саме на URI (адресу) запиту|
|`content:"rule"`|Шуканий вміст|Перевіряє, чи міститься слово `rule` у URI запиту|
|`fast_pattern`|Оптимізація|Каже Suricata використовувати саме цей `content` як найшвидший спосіб попередньо відфільтрувати пакети (для продуктивності — перевіряється першим, до повного матчингу правила)|
|`classtype:bad-unknown`|Класифікація|Категорія загрози — тут "потенційно погана, але невизначена" активність|
|`sid:123`|Signature ID|Унікальний ідентифікатор правила (обов'язковий, має бути унікальним у всій базі правил)|
|`rev:1`|Revision|Номер версії/ревізії правила (збільшується при редагуванні)|

---

Це **інший** тип алертів, з вищим пріоритетом (`Priority: 1` — серйозніший, ніж `Priority: 2`). IP-адреси `91.189.91.81` і `91.189.91.83` належать **Canonical** (компанія-розробник Ubuntu) — це офіційні сервери оновлень/пакетів Ubuntu (`archive.ubuntu.com`, `changelogs.ubuntu.com` тощо).

Класифікація **"Potential Corporate Privacy Violation"** в ET/GPL правилах зазвичай спрацьовує на HTTP-трафік, що містить певні ідентифікуючі рядки в заголовках (наприклад, специфічний User-Agent, деталі версії ОС чи пакетного менеджера, які "видають" інформацію про систему стороннім серверам) — типова причина: фонові процеси Ubuntu (наприклад перевірка оновлень `apt`, `snap`, або `motd-news`) роблять автоматичні HTTP-запити, і Suricata за замовчуванням трактує такий трафік як потенційний витік даних про систему.


![[Pasted image 20260724010308.png]]
**Багато повторів однакового алерту**  — типова картина, коли фонова служба Ubuntu періодично "стукає" на ці сервери (наприклад перевірка оновлень раз на якийсь інтервал), і кожне таке з'єднання генерує новий алерт. 
Це **false positive** (хибне спрацювання) на легітимний, штатний трафік Ubuntu — не атака, а звичайна фонова активність системи оновлень, яку правило класифікувало як "потенційний витік корпоративних даних" через специфічний патерн у HTTP-заголовках.
